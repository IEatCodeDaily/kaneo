# KFL-367 — Scoped Ticket Membership and Project Progress implementation spec

## Gate and premise audit

**PASS:** KFL-366 `spec-review` and `qc-review` are recorded `pass`; its uncommitted QC-passed worktree supplies Project foundation migration `0072`, the `/api/project` router, Project resource-lattice access, slug resolution, Project web routes, and org-scoped Project sync invalidation.

**Verdict: implementable as an additive cutover on KFL-366.** The architecture binds this ticket to an explicit `project_ticket` association, not `task.projectId`. `task.boardId`, board key/number identity, workflow status/column, archival state, and board membership remain untouched. Existing Project projections deliberately return `progress: null`; replace that presentation-only value with an API-derived, authorization-filtered aggregate.

Findings governing implementation:

- `projectTable` and `projectSlugAliasTable` now exist in `schema.ts` and migration `0072`; the next migration number must be determined from the current migration journal immediately before implementation. Do not amend `0072`.
- Tasks belong to Boards; Board organization is available through `boardTable`. This is the only valid organization proof for a ticket.
- `task.status` uses the canonical `status-taxonomy.ts`: only `done` is complete; `canceled` and `duplicate` are excluded. Archived (`archivedAt`) and deleted (`deletedAt`) are orthogonal to status and are ineligible.
- Project access and Board access are independently enforced by `organizationAccess` plus the resource lattice. Project membership must never turn Project visibility into Board/Ticket visibility, nor Board visibility into Project visibility.
- `project-projection.ts`, `project-overview.tsx`, `project-row.tsx`, and the root Project detail route currently hard-code the KFL-366 empty state. Update every projection consumer and test rather than retaining a compatibility helper.
- Existing project pushes (`registerProjectSyncBroadcast` and `invalidateProjectQueries`) refresh Project list/detail caches. Membership mutations and task changes that affect a scoped ticket must publish through this pathway; otherwise progress becomes stale in another tab.

## Persistence

### `project_ticket`

Create `projectTicketTable` mapped to `project_ticket`:

| Column | Contract |
|---|---|
| `id` | CUID2 text primary key; immutable association identity. |
| `project_id` | Non-null FK to `project.id`, cascade delete/update. |
| `task_id` | Non-null FK to `task.id`, cascade delete/update. |
| `rank` | Non-null integer default `0`; only ordering metadata. |
| `added_by` | Non-null FK to `user.id`; restrict delete, cascade update. |
| `added_at` | Non-null timestamp default now. |

Constraints and indexes:

- unique `task_id` across all rows: v1 permits zero-or-one Project membership per ticket;
- unique `(project_id, task_id)` as defensive relation identity;
- indexes `(project_id, rank)` for ordered Project projections and `task_id` for membership lookup on task lifecycle changes;
- no `organization_id` duplication and no `task.projectId` column.

The database FKs cannot prove same organization because the task reaches its organization through `board`. The add controller must prove `project.organizationId === task.board.organizationId` in the same transaction that inserts the association. A duplicate task association returns `409`; a foreign-org Project/Ticket combination returns a non-leaking `404` for the inaccessible side or `400` only after both resources are discoverable to the caller. Remove is idempotency-sensitive: return `404` when the association is absent and never write Task fields.

No Project Milestone table or `project_ticket.project_milestone_id` is in this ticket. Architecture section 3.7 permits it as optional; KFL-367 does not introduce Project Milestones.

## Derived projection and progress contract

Replace `withPresentationOnlyFields()` in `apps/api/src/project/project-projection.ts` with one shared projection builder used by Project list, get, resolve, Overview, and Tickets tab.

Return:

```ts
type ProjectProgress = {
  completed: number;
  eligible: number;
  percent: number | null;
};
```

`percent` is `completed / eligible * 100` (unrounded machine value; UI owns formatting) or `null` when `eligible === 0`. `progress` is this object, not a stored field and not `0` for empty scope. The client renders `No scoped work` only for `percent === null`.

For **each requesting user**, derive both progress and Project Ticket rows from the same visible membership set:

1. Start with `project_ticket` rows for the Project.
2. Join Task and Board; include only tickets whose Board grants the requester `view` via the existing resource lattice.
3. Exclude `task.deletedAt IS NOT NULL` and `task.archivedAt IS NOT NULL` from eligible work.
4. Exclude statuses `canceled` and `duplicate` from eligible work.
5. Count status `done` as completed; all remaining eligible statuses are incomplete.

This per-request filtering is required: a Project grant never grants Board/Ticket access, and aggregate counts/percentages must not infer inaccessible ticket existence or state. Do not return a total membership count unless it has the same visibility filter. Project list rows and direct/slug Project resolution must use the same contract. `health` remains `null` / `No update` until the Updates ticket.

Project Ticket item projection contains only authorization-safe ticket presentation data: `id`, `boardId`, `boardSlug`, `boardName`, `number`, canonical `key` (`${boardSlug}-${number}`), `title`, `status`, `priority`, `archivedAt`, and membership `rank`, `addedAt`, `addedBy`. Its route is `/dashboard/organization/:organizationSlug/board/:boardSlug/task/:taskId`. Do not expose description, comments, assignees, labels, or any ticket not individually visible.

## API

Extend `apps/api/src/project/index.ts`; preserve Project root middleware and OpenAPI/Valibot conventions. Add thin handlers and controllers under `apps/api/src/project/controllers/`.

| Endpoint | Middleware and authorization | Controller contract |
|---|---|---|
| `GET /project/:id/tickets` | `fromProject`, `project:read`, Project `view` guard | `list-project-tickets`; returns only Board-viewable scoped ticket projections and the requester-filtered progress. |
| `POST /project/:id/tickets` | `fromProject`, `project:update`, Project `edit` guard; independently resolve task using `fromTask`-equivalent access before mutation; require `task:update` and Board `edit` | `add-project-ticket`; body `{ taskId, rank? }`; prove same org and no existing Project membership atomically; insert only association metadata. |
| `DELETE /project/:id/tickets/:taskId` | Same Project and Task edit/action checks as add | `remove-project-ticket`; delete only the matching association, never the Task or its Board metadata. |

Do not overload `PUT /project/:id`, `POST /task`, bulk task operations, or Board milestone routes with Project membership. There is no generic resource-link endpoint in this ticket.

Controllers and the shared projection must use set-based joins/aggregates; do not query access/membership once per Ticket. Reuse `listAccessibleResourceIds` (or add one narrowly reusable Board-visible-ID helper beside it) to intersect the task query with visible Board IDs. If no Boards are visible, return an empty ticket list and null progress without querying an unbounded task set.

### Event and cache cutover

- `add-project-ticket` and `remove-project-ticket` publish `project.updated` with `organizationId` and `projectId` after commit, so existing `registerProjectSyncBroadcast()` emits `PROJECT_UPDATED` and web clients call `invalidateProjectQueries(queryClient, projectId)`.
- Any existing Task mutation that changes a scoped ticket's progress eligibility or completion — status update, archive/unarchive, soft delete/restore, permanent delete, and a board move — must look up affected `project_ticket` rows before/within its transaction and publish `project.updated` for each affected Project after commit. A task moved across organizations must atomically remove its membership rather than leave an invalid cross-org association.
- Do not broadcast ticket projection data or membership counts; the client refetches through the authorization-filtered Project API.
