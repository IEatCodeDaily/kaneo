# KFL-368 — Contextual Project Resource links implementation spec

## Gate and premise audit

**PASS:** KFL-368 `spec-review` is `in-progress`. KFL-366 is present as an uncommitted, QC-passed worktree implementation and is the required base: migration `0072_project_foundation.sql`, Project schema/relations, `/api/project`, Project resource-lattice visibility, slug resolution, Overview-first routes/components, and Project sync broadcast/query invalidation all exist in the diff.

**Verdict: implementable, with three architecture constraints.** Section 3.6 and accepted ADR 18 require dedicated type-safe association tables and one unified API projection. Resource links are context only: they grant no privilege, contribute no progress, and never transfer ownership.

- No Project Resource link tables, controllers, endpoints, fetchers, hooks, picker, or contextual-resource UI currently exist.
- Use `project_board`, `project_repo`, and `project_table_link`; do not introduce `domain_resource_link` or accept an unchecked polymorphic ID.
- Same-Organization must be database-backed on every association. `project` and `board` already expose unique `(organization_id,id)` keys; add equivalent composite unique keys to `repo` and `data_table`, then use composite foreign keys from every link table to both Project and target Resource.
- Discoverability is conjunctive. A caller must have Project `view` and target Resource `view` to see or create a link. Project edit permission alone must not reveal candidate or linked Resource metadata.
- Link creation does not create or modify `resource_grant`; link deletion/project deletion/project archive does not mutate the Resource; Resource deletion removes only its association rows. Project archive preserves its links for historical Overview display.
- KFL-366 returns `progress: null`. KFL-368 must leave that contract unchanged. Contextual links never feed future Project Ticket progress.
- KFL-366 already publishes `project.updated`, fans it out through `registerProjectSyncBroadcast`, and invalidates via `invalidateProjectQueries`; link mutations must reuse that exact event path rather than add a second socket message or cache convention.

## Persistence

Create **`apps/api/drizzle/0073_project_resource_links.sql`**, its generated snapshot, and the journal entry following `0072`. Modify `apps/api/src/database/schema.ts`, `relations.ts`, and `database/index.ts`.

Add `unique("repo_organization_id_id_unique").on(repo.organizationId, repo.id)` and `unique("data_table_organization_id_id_unique").on(dataTable.organizationId, dataTable.id)` so association tables can enforce organization identity with composite foreign keys. Do not alter Resource identity or existing single-column primary keys.

All three association tables have the same metadata contract but remain independent Drizzle tables:

| Column | Contract |
|---|---|
| `id` | CUID2 `text` primary key; stable link identity. |
| `organization_id` | non-null Organization FK, cascade delete/update. |
| `project_id` | non-null. Composite FK `(organization_id,project_id)` → `project(organization_id,id)`, cascade delete/update. |
| typed Resource ID | non-null `board_id`, `repo_id`, or `table_id`. Composite FK `(organization_id,<resource_id>)` → matching Resource `(organization_id,id)`, cascade delete/update. |
| `relationship` | non-null text; check exactly `context|dependency|deliverable`. |
| `label` | nullable text; optional display override, trimmed; blank normalizes to NULL. |
| `note` | nullable text; optional context, trimmed; blank normalizes to NULL. |
| `rank` | non-null integer default `0`; non-negative check. Ordering is `rank`, then `created_at`, then `id`. |
| `created_by` | non-null User FK; `restrict` delete, cascade update. |
| `created_at` | non-null timestamp default now. |

Per-table constraints/indexes:

- Unique `(project_id, board_id)`, `(project_id, repo_id)`, or `(project_id, table_id)`; one semantic link per Project/Resource. Relationship and metadata are updated on that row rather than duplicated.
- Index `project_id`; index the typed Resource ID; index `(project_id,rank)` for ordered unified reads.
- Export `projectBoardTable`, `projectRepoTable`, and `projectTableLinkTable` through the Drizzle schema object.
- Relations: Project has `boardLinks`, `repoLinks`, `tableLinks`; each link has `organization`, `project`, typed Resource, and `creator`; each Resource has `projectLinks`.

Deletion semantics are intentionally FK-driven: deleting a Project or Resource cascades only association rows. Archiving or unlinking issues no Resource update/delete. Organization deletion may cascade all owned rows as it already does.

## API

Extend `apps/api/src/project/index.ts`; create controllers beneath `apps/api/src/project/controllers/resources/` and shared contracts in `apps/api/src/project/project-resource-projection.ts`. Keep the existing `/api/project` router and Project middleware chain.

Unified public shapes:

```text
ProjectResourceLink = {
  id, projectId, resourceType: "board"|"repo"|"table", resourceId,
  relationship: "context"|"dependency"|"deliverable",
  label, note, rank, createdBy, createdAt,
  resource: type-specific safe summary
}
```

Safe summaries contain only navigational display data already exposed by each Resource list API:

- Board: `{id, slug, name, icon, archivedAt}`.
- Repo: `{id, owner, name, provider, url, description, isActive}`; never `config`, installation credentials, or provider tokens.
- Table: `{id, name, icon}` using actual `data_table` columns; no fields, rows, or cells.

Endpoints:

| Endpoint | Middleware and authorization | Controller contract |
|---|---|---|
| `GET /project/:id/resources` | param validator; `organizationAccess.fromProject()`; `project:read`; Project `view` | `list-project-resources`: union the three tables in stable order, apply target `listAccessibleResourceIds`/`view` filtering per type before projection, omit inaccessible rows completely. |
| `POST /project/:id/resources` | param/body validators; `fromProject`; `project:update`; Project `edit`; target Resource `view` | `create-project-resource-link`: body `{resourceType,resourceId,relationship,label?,note?,rank?}`; controlled switch selects exactly one table; verify target exists in same org and is discoverable; insert; duplicate returns 409; missing/cross-org/inaccessible target returns identical 404 `Resource not found`. |
| `PUT /project/:id/resources/:linkId` | params/body validators; `fromProject`; `project:update`; Project `edit`; linked target still `view` | `update-project-resource-link`: body is full mutable metadata `{relationship,label,note,rank}`; link lookup is Project-scoped; inaccessible/missing link returns identical 404 `Resource link not found`; resource type/ID are immutable. |
| `DELETE /project/:id/resources/:linkId` | params validator; `fromProject`; `project:update`; Project `edit`; linked target `view` | `delete-project-resource-link`: delete association only; inaccessible/missing link returns identical 404; return 204. |

Implementation details:

- Add a shared `PROJECT_RESOURCE_RELATIONSHIPS` const and Valibot picklist. Reject unknown `resourceType`, relationship, negative/non-integer rank, and extra ambiguous typed IDs at validation.
- Project guards follow KFL-366's organization permission plus resource privilege lattice. Target guards use canonical `requireResourcePrivilege`, never Organization membership alone.
- Never return a placeholder, hidden count, typed ID, relationship, rank, or link existence for an inaccessible target. Filtering occurs before serialization.
- Creation same-org validation is both controller-level (for uniform no-leak 404) and FK-backed (for race/integrity safety). Translate unique violations to 409 and do not expose database identifiers in errors.
- After successful create/update/delete, publish existing `project.updated` with `{organizationId,projectId}`. Do not create Resource events and do not mutate `project.updatedAt` unless repository convention explicitly treats relationship changes as Project updates; event invalidation is required either way.
- Do not add link data to list-project projections. Extend the detail Overview through its dedicated resources query, avoiding N+1 visibility work on the Projects list.

## Web

- Fetchers in `apps/web/src/fetchers/project/`: `get-project-resources.ts`, `create-project-resource-link.ts`, `update-project-resource-link.ts`, `delete-project-resource-link.ts`. Mirror the typed Hono-client/error pattern in `get-project.ts` and `update-project.ts`.
- Query hook `apps/web/src/hooks/queries/project/use-get-project-resources.ts`; query key `['project-resources', projectId]`.
- Mutation hooks in `apps/web/src/hooks/mutations/project/`: `use-create-project-resource-link.ts`, `use-update-project-resource-link.ts`, `use-delete-project-resource-link.ts`. On success call `invalidateProjectQueries(queryClient, projectId)` and invalidate `['project-resources', projectId]`. Extend `invalidateProjectQueries` itself to invalidate the `project-resources` family so WebSocket `PROJECT_UPDATED` refreshes links across tabs/users.
- Components in `apps/web/src/components/project/`: `project-contextual-resources.tsx`, `project-resource-row.tsx`, `project-resource-link-dialog.tsx`, and `project-resource-unlink-dialog.tsx`, with colocated tests. Integrate `ProjectContextualResources` into existing `project-overview.tsx`; do not create a second Project route or Board-style layout.
- Mirror Resource sources rather than inventing endpoints: `useGetBoards`, `useGetRepos`, and `useDataTables` already return visibility-filtered organization resources. The link dialog groups Board/Repository/Table candidates, excludes already-linked IDs, requires relationship, and exposes optional label/note. Reuse existing dialog, select/menu, input, textarea, badge, and empty-state primitives.
- `project-contextual-resources.tsx` renders a titled section separate from the existing `No scoped work` section. Rows show type icon, safe name, relationship badge, optional label/note, and link to the canonical Resource route. Edit/unlink controls appear only when Project update/edit capability is available; merely viewing a link never implies target edit rights.
- Keep scoped-ticket presentation separate even while KFL-366 still renders the `No scoped work` placeholder. No combined “work/resources” count, progress bar, or fallback that treats Board links as Ticket scope.
- Loading, empty, and inaccessible cases disclose no hidden row/count. At 375px, rows wrap metadata and keep resource navigation plus overflow actions usable.
