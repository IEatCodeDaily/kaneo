**Premise reconciliation with the architecture (sections 2.8, 3.5, 4.4, 6.3,
9, 11, 13 Task 11).** Every load-bearing rule in the ticket is already encoded
in the architecture:

- **Authored, not derived, health.** §2.8 separates lifecycle (declared),
  progress (mechanical), health (authored judgment from the latest update), and
  archive (visibility). §3.5 + §4.4 make "latest health = newest update" the
  binding contract. §11 explicitly rejects "Automated or AI-authored health" and
  "Estimate-weighted progress". The implementer MUST NOT add a "compute health
  from progress" path, MUST NOT mutate authored health on Ticket status change,
  and MUST NOT store `no-update` as a health value.
- **"No update" is presentation-only.** §3.5 and §4.4 both state that the empty
  state is a presentation, not a stored value. The schema stores zero rows in
  that case; the UI renders `No update`.
- **Staleness is a presentation threshold.** §4.4 lists "presentation warning
  when the latest Update is stale beyond a configurable display threshold" as
  the only acceptable behavior. The threshold MUST live in code (a single named
  constant in the API and the web) and MUST NOT be a stored column.
- **Edit attribution per existing comment/description-history conventions.**
  §3.5 explicitly says "immutable edit history or edited timestamp according to
  existing collaboration conventions." The repo's existing convention is the
  `activityTable.editHistory` jsonb `Array<{ content, editedAt, userId }>`
  model plus the `taskTable.descriptionHistory` `Array<{ content, editedAt,
  userId, sealed? }>` compression model. KFL-370 reuses the `editHistory` shape
  verbatim, NOT the `descriptionHistory` compression (compression is a
  description-only affordance tied to the "close task" lifecycle; an Update is
  an authored narrative that should retain every edit attributable to its
  author). A single, named helper `appendUpdateEdit` lives next to
  `appendDescriptionRevision` and is the only place that mutates the array.
- **Push-driven freshness; recipient semantics are NOT specified yet.**
  §9 (Event and cache contract) and Task 11 both require org-scoped push for
  every visible mutation. §13 Task 11 explicitly says "Wire
  notification/follower behavior only after recipient semantics are specified."
  KFL-370 emits push events for cache invalidation and projects health, but
  does NOT write `notificationTable` rows and does NOT touch follower/subscribe
  state. See "Explicit out of scope".
- **Domain type + ID, or separate type-safe tables.** §3.5 allows either. The
  repo precedent (every other Project relationship has its own type-safe table:
  `project_slug_alias`, future `project_ticket`, `project_milestone`,
  `project_team`) plus the existing `resource-grant` polymorphic-fk discussion
  in §8.4 argues for a dedicated `project_update` table now and a parallel
  `initiative_update` table once KFL-371 begins. Sharing one `domain_update`
  table would force a polymorphic Resource FK and a same-Organization resolver
  that does not exist yet. KFL-370 adds `project_update` only.

### `project_update`

`projectUpdateTable` columns:

| Column | Contract |
|---|---|
| `id` | CUID2 `text` PK; opaque immutable ID. |
| `project_id` | non-null `project` FK; cascade delete/update (a Project and its Updates die together — an orphaned Update has no canonical parent). |
| `organization_id` | non-null `organization` FK; cascade delete/update (defense-in-depth: an Update can never outlive its Organization even if a future migration drops the Project FK). |
| `author_id` | non-null `user` FK; restrict delete, cascade update. The author identity is preserved exactly as it was at publish time. |
| `content` | non-null `text`. Rich-content payload — Markdown, plain text, or whatever the existing `comment.content`/`activityTable.content` shape allows. KFL-370 does not introduce a new content type; it stores the same `string` shape the activity feed already uses. |
| `health` | non-null `text`. CHECK constraint `'on-track' \| 'at-risk' \| 'off-track'`. No `no-update` value. The empty state is "no row" (presentation), never a row with a sentinel health. |
| `edit_history` | non-null `jsonb` default `'[]'`. `$type<Array<{ content: string; editedAt: string; userId: string }>>()`. Same shape as `activityTable.editHistory`; no `sealed` flag, no compression window (see "edit attribution" rationale above). |
| `created_at` | non-null default `now()` timestamp. |
| `updated_at` | non-null default `now()` timestamp with `.$onUpdate(() => new Date())`. Mirrors `activityTable.updatedAt` exactly. |

Constraints / indexes:

- CHECK on `health` value set: `('on-track', 'at-risk', 'off-track')`. Use the
  same `DO $$ BEGIN ... EXCEPTION WHEN duplicate_object THEN null; END $$;`
  pattern as 0072 so the migration is idempotent on re-run.
- Composite index `(project_id, created_at desc)` for the "latest update" and
  the paginated history query.
- FK-supporting index on `author_id`.
- FK-supporting index on `organization_id` (cheap; supports the access-check
  join for the "list accessible updates" read).

There is NO `project_update_slug_alias` (Updates have no URL surface, no
canonical identity, no rename). There is NO `project_update_<x>` table for
reactions, attachments, or threaded replies — those are explicit non-goals
(§11 + ticket).

### `project_update_edit_history` (no separate table)

The architecture's existing `editHistory` jsonb is the entire edit-attribution
mechanism. KFL-370 MUST NOT add a separate `project_update_edit` table; the
jsonb on the row is the source of truth and is never reconstructed from a
side table.

## Edit attribution helper

Create `apps/api/src/project/utils/append-update-edit.ts`:

```ts
export type UpdateEdit = { content: string; editedAt: string; userId: string };

/**
 * Append a pre-edit snapshot of `previousContent` to an Update's edit history.
 *
 * Mirrors `updateComment`'s append semantics: the array stores the content
 * as it was BEFORE each edit, so a future UI can reconstruct prior versions.
 * The compression window used by `appendDescriptionRevision` is intentionally
 * NOT applied — an Update is an authored narrative, not a free-form
 * description, and rapid successive edits by the same author still warrant
 * attributable revisions.
 */
export function appendUpdateEdit(
  history: UpdateEdit[],
  previousContent: string,
  userId: string,
): UpdateEdit[];
```

Tests for this helper live next to the helper (`append-update-edit.test.ts`)
using vitest. Mirror the structure of `apps/api/src/task/utils/description-history.ts`
unit tests: feed in a known history, assert the appended shape, assert no
compression, assert edit history is append-only (no in-place mutation).

## Explicit out of scope

The implementer MUST refuse to implement any of the following, with the
rationale recorded in the work log. Each is a future ticket.

- **Followers / subscriptions / notifications.** §13 Task 11 explicitly
  defers "Wire notification/follower behavior only after recipient
  semantics are specified." No `notificationTable` writes, no follower
  table, no `userProjectFollow` join, no email. The push event payload
  carries `{ organizationId, projectId, updateId, health }` for cache
  invalidation; it does NOT carry a recipient list because no list is
  defined. Future ticket: KFL-372 (or follow-on) once recipient
  semantics are ratified.
- **Health revision history.** Only `content` edits are tracked in
  `edit_history`. A change to `health` overwrites the field; no
  per-update health timeline is stored. The architecture allows a
  separate `update_health_history` table; KFL-370 does not add it. If a
  product need emerges, it gets its own ticket.
- **Reactions, attachments, threaded replies, mentions.** All
  architecture-explicit non-goals for Update v1. A future
  `project_update_reaction` table is allowed but not implemented.
- **Initiative Updates.** §3.4 + §3.5 describe a parallel
  `initiative_update` table for Initiative objects. KFL-370 ships
  `project_update` only. Initiative Updates are a separate ticket (likely
  KFL-371 or follow-on). The shared `appendUpdateEdit` helper is
  designed to be Initiative-Update-agnostic (the function signature does
  not name "project" or "initiative") so the future Initiative table can
  consume it without a copy.
- **Polymorphic `domain_update` table.** §3.5 allows one shared table
  with `(domain_type, domain_id)`. KFL-370 deliberately chooses
  type-safe `project_update` to keep the FK chain ordinary (no
  polymorphic-fk resolver required) and to mirror the existing
  `project_ticket` / `project_milestone` / `project_team` type-safe
  pattern. The decision is recorded here so the Initiative ticket
  knows the precedent.
- **Archive-vs-Update interaction beyond the cascade FK.** KFL-370
  does not introduce "archived Projects hide their Updates from the
  Projects overview" filtering; the Project list query already
  filters by `archivedAt`, and the Updates sub-router continues to
  serve archived Projects' history (the test plan's case 14 commits
  to "Updates survive archive"). If the product wants to hide them
  later, it's an additional filter, not a schema change.
- **Storing staleness.** §4.4 forbids it. The threshold is a web-only
  constant. There is no `isStale` column.
- **Storing `no-update` as a health value.** §3.5 + §4.4 forbid it.
  The CHECK constraint rejects it; the empty state is rendered from a
  zero-row query, not a sentinel row.
- **Permission lattice changes.** KFL-370 reuses `project:read` for
  the list and `project:update` for create/edit/delete. No new
  `project:comment` or `project:share` action. Future grants work
  will revisit if needed.
- **Progress → health inference.** §2.8 + §4.4 forbid it. The
  implementer MUST NOT add a "health computed from progress %"
  branch anywhere. The integration test case 10 nails this.
- **Per-Project staleness threshold configuration.** §4.4 says
  "configurable display threshold" but the v1 deliverable uses a
  single global constant. A future ticket can add a per-Project
  override column; not in scope now.
- **Reuse of an existing rich-text / Markdown editor.** KFL-370 uses
  a plain `<textarea>` for the composer to avoid pulling in a new
  editor dependency mid-Project-foundation. The `comment` activity
  feed already accepts plain text; the Update content type matches.
  A future ticket can adopt the same rich editor the team chooses
  for Activity; KFL-370 does not block that.
